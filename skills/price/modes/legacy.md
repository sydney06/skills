# /price legacy basis

Read for a line whose Basis is `legacy` (it replaces `audit` steps 3 to 5), and by `quote` for steps 1 and 2.

Weights: the Active row of `size-weights.md`. Rate: contract rate. Commit dates only show when the work was built (no sessions, no measured hours).

1. **Size score** = the weighted sum of the step 2 signals. Counting rules: a thin admin proxy handler (a pass through to the backend with no logic of its own, about 25 to 50 lines) is a Component, not a Route; backend endpoints and admin handlers with real logic stay Routes. A cron change is a Background job only when it creates a new job file or a new schedule; extending an existing job counts as lines. Moved lines (relocated, content unchanged) count nowhere, like renames; list them. → each signal x weight printed.
2. **Calibrate.** Anchors with a known time come first: the rows of the `Known time anchors` table in `size-weights.md` (a ledger line, the hours the owner confirmed). Find each one's commits as in step 2, owner confirms as in step 1, score it under the Active weights; leave out, and name, an anchor with none. Per anchor: hours per point = its hours / score. **Rate** = that anchor's hours per point when there is one anchor, the median when several; lowest and highest give low and high. A feature that is itself an anchor takes its stated hours as its solo hours. The reference items (the `Reference items` table in `size-weights.md`; commits found as in step 2, solo hours = valuation / contract rate, hours per point = solo hours / score; a Waived item excluded; leave out, and name, an item with none) are the rate only when no known time anchor exists, and always a cross check column. → the table, with rate, lowest, highest and the cross check median.
3. **Fee.** Solo hours = score x rate. Proposed fee = solo hours x contract rate, nearest 5. Low and high: the same with the lowest and highest hours per point, each nearest 5. Name the anchor closest by score. Confidence: with known time anchors, **Medium** only when two or more were found and (high minus low) / proposed fee is 0.5 or less, else **Low**; one anchor is **Low** with the reason `single known-time anchor`, and the audit also states the cross check fee (score x its median x contract rate) and how far it differs from the proposed fee. With the reference items fallback, **Medium** when at least three items were found and the same spread is 0.5 or less, else **Low**. → all printed.
4. **Step 6:** the increment starts on the 1st of the calendar month after the Retroactive SOW is acknowledged: the ledger's `SOW acknowledged` cell, which `sow <feature> ack` fills. Empty → ask the owner for that date (recommend pending until it is acknowledged); a date they give goes in that cell, else the retainer effect stays pending. The deployment date is information only. Step 7 uses the template's legacy variant, with the literal `n/a (legacy: contract rate)` as the rate and speed factor, in the audit file and the ledger alike. Step 8 offers `/price sow <feature> register` as a Retroactive SOW with the audited fee as its estimate, when the line has no SOW no. → increment start dated, or pending the acknowledgement date.
